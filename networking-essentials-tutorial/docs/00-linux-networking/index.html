    Module 0: Linux Networking Essentials for Backend Engineers

    Duration: 2–3 hours | Level: Beginner→Intermediate | Prerequisites: Basic command-line comfort, ability to SSH into a Linux box

    What This Module Is: An exhaustive, hands-on guide to the Linux networking tools and concepts that every backend and DevOps engineer must know. You will learn how to inspect, troubleshoot, configure, and optimize network behavior on any Linux system.

    0.1 Introduction & Context

    Why You Need This

    Linux powers approximately 96% of the cloud infrastructure on the planet. When your Flask API mysteriously drops connections, when a Kubernetes pod can't reach the database, or when a load balancer returns 502 errors — the problem is almost always solved by understanding and inspecting the Linux networking layer.

    Most networking tutorials focus on protocols (TCP/IP theory), cloud services (AWS VPCs), or web frameworks. But they skip the actual tools you will use at 3 AM to debug production. This module fills that gap.

    The Reality of Production Debugging

    You will encounter these scenarios:

    1. "The database connection timed out" — You SSH into the application host and discover port 5432 is not being routed correctly.
    2. "WebSocket connections drop every 5 minutes" — You use tcpdump to find that a firewall rule is silently killing idle connections.
    3. "Kubernetes DNS works from one pod but not another" — You hop into the pod's network namespace and inspect interface configuration.
    4. "The API is slow but CPU and memory look fine" — You check ethtool statistics and discover the network card is dropping packets due to buffer overflow.

    In all these cases, the Linux tools in this module are your only path to truth.

    Historical Evolution of Linux Networking Tools

    Linux has had several generations of networking tools:

    Era Tools Limitation Current Status
    1990s–2000s ifconfig, route, netstat, arp Slow (parses /proc), poor IPv6 support Deprecated
    2000s–2010s iproute2 suite (ip, ss) Fast, complete, but steeper learning curve Current standard
    2010s–Present ip, ss, nftables, bpf tools Modern, scriptable, kernel-aware Actively maintained

    You will see the old tools in legacy documentation and older systems, but know ip and ss first.

    Mental Model for This Module

    ┌─────────────────────────────────────────────────────┐
│  Application (Flask, Node.js, Go)                    │
├─────────────────────────────────────────────────────┤
│  System Call Layer (bind, listen, connect, send)     │
├─────────────────────────────────────────────────────┤
│  Linux Kernel Networking Stack                       │
│  ├─ Socket management                                │
│  ├─ Protocol handlers (TCP, UDP, ICMP)               │
│  ├─ Routing decisions                                │
│  ├─ Firewall rules (iptables/nftables)               │
│  └─ Interface drivers                                │
├─────────────────────────────────────────────────────┤
│  Network Hardware (NIC driver, physical interface)    │
├─────────────────────────────────────────────────────┤
│  Physical Network (switches, routers, cables)         │
└─────────────────────────────────────────────────────┘

    Throughout this module, we inspect each layer. Most problems live in the kernel and hardware layers, not in your application code.

    0.2 Network Interfaces: The Foundation

    What Is a Network Interface?

    A network interface is an abstraction representing how your host connects to a network. It may be:

    • Physical – a real ethernet port (eth0), wifi card (wlan0)
    • Virtual – created by software for containers (veth123...), tunnels (tun0), or bridges (br0)
    • Loopback – only for localhost traffic (lo)

    Each interface has: - A name (eth0, docker0, wlan0) - MAC address (hardware layer, 00:11:22:33:44:55) - IPv4 address(es) (192.168.1.100/24) - IPv6 address(es) (fe80::1/64) - State (UP, DOWN) - MTU (maximum transmission unit, usually 1500 bytes)

    Inspecting Interfaces: The ip Command

    The ip suite of tools is the modern standard. Think of it as a single powerful binary with subcommands.

    Basic Inspection

    # Show all interfaces with addresses
ip addr show

# output:
# 1: lo: <LOOPBACK,UP,LOWER_UP> mtu 65536 qdisc noqueue state UNKNOWN group default qlen 1000
#     inet 127.0.0.1/8 scope host lo
#     inet6 ::1/128 scope host
#
# 2: eth0: <BROADCAST,MULTICAST,UP,LOWER_UP> mtu 1500 qdisc fq_codel state UP group default qlen 1000
#     link/ether a2:34:56:78:90:ab brd ff:ff:ff:ff:ff:ff
#     inet 192.168.1.100/24 brd 192.168.1.255 scope global dynamic eth0
#     inet6 fe80::a034:56ff:fe78:90ab/64 scope link

    Breaking down the output:

    • <LOOPBACK,UP,LOWER_UP> = flags indicating state
    • UP = interface is administrative up (layer 3)
    • LOWER_UP = physical/driver layer is operational (layer 1)
    • LOOPBACK = reserved for localhost
    • BROADCAST = can send broadcast frames

    • MULTICAST = can send multicast frames

    • mtu 1500 = maximum frame size before fragmentation (1500 is standard Ethernet)

    • inet 192.168.1.100/24 = IPv4 address with CIDR, brd is broadcast address

    • inet6 fe80::1/64 = IPv6 address (link-local by default on Ethernet)

    • scope values:

    • global = routable on external networks
    • link = only on local segment
    • host = localhost only

    Show a Specific Interface

    # Show only eth0
ip addr show eth0

# Show only IPv4
ip -4 addr show

# Show only IPv6
ip -6 addr show

    Add an Address (Temporarily)

    # Add a second IP to eth0
sudo ip addr add 192.168.1.50/24 dev eth0

# Verify
ip addr show eth0 | grep "inet 192.168.1.50"

# Remove it
sudo ip addr del 192.168.1.50/24 dev eth0

    Check Interface Statistics

    # Show RX/TX statistics
ip -s link show eth0

# output:
# 2: eth0: <BROADCAST,MULTICAST,UP,LOWER_UP> mtu 1500 qdisc fq_codel state UP mode DEFAULT group default qlen 1000
#     link/ether a2:34:56:78:90:ab brd ff:ff:ff:ff:ff:ff
#     RX: bytes  packets  errors  dropped overrun mcast
#     268402    1843     0       12      0       0
#     TX: bytes  packets  errors  dropped carrier collsns
#     198761    1204     0       0       0       0

    What the metrics mean:

    • RX bytes/packets = total data received / number of frames received
    • errors = corrupted frames (usually hardware issues)
    • dropped = frames discarded by kernel (usually insufficient buffer or firewall DROP rule)
    • overrun = interface couldn't keep up with incoming traffic (ring buffer too small)

    0.3 Routing: Where Packets Go

    Understanding the Routing Table

    The routing table is a list of rules: "To reach network X, send packets through gateway G via interface I".

    Inspecting Routes: The ip route Command

    # Show entire routing table
ip route show

# output:
# default via 192.168.1.1 dev eth0 proto dhcp metric 100
# 192.168.1.0/24 dev eth0 proto kernel scope link src 192.168.1.100
# 10.0.0.0/8 via 192.168.1.254 dev eth0 metric 200

    Breaking it down:

    • default via 192.168.1.1 dev eth0 = "For any address not listed below, send to 192.168.1.1 via eth0"
    • proto dhcp/kernel/static = how the route was added (DHCP server, kernel auto-detect, manual)
    • metric 100 = cost (lower = preferred). When multiple routes match, lowest metric wins
    • 192.168.1.0/24 dev eth0 scope link = directly connected subnet (no gateway needed)

    How Routing Works: A Walkthrough

    When your application sends a packet to 8.8.8.8:

    1. Kernel checks routing table for longest matching prefix
    2. 8.8.8.8 doesn't match 192.168.1.0/24 or 10.0.0.0/8
    3. Falls back to default via 192.168.1.1
    4. Sends packet to 192.168.1.1 (your gateway/router) via eth0
    5. Router decides where to forward it next

    Key insight: Routing is prefix matching, not exact matching. The most specific (longest prefix) match wins.

    Adding and Deleting Routes

    # Add a route to a specific network via a gateway
sudo ip route add 192.168.50.0/24 via 192.168.1.254 dev eth0

# Verify
ip route show

# Delete the route
sudo ip route del 192.168.50.0/24

# Add a default route (if none exists)
sudo ip route add default via 192.168.1.1

    Temporary vs Persistent Routes

    The routes you add with ip route are temporary — they vanish when you reboot.

    For persistence, edit /etc/network/interfaces (Debian/Ubuntu) or /etc/sysconfig/network-scripts/ifcfg-eth0 (RHEL/CentOS), or use netplan on modern systems.

    Routing Table Pitfalls

    Critical: You Can Lock Yourself Out

    If you're SSH'd into a remote server and you delete the default route, you lose connectivity immediately. Always test local systems first.

    # DANGEROUS on remote system!
sudo ip route del default
# ... now you can't connect to the server anymore!

    0.4 Sockets: Listening and Connections

    What Is a Socket?

    A socket is an endpoint for network communication — the kernel's representation of a connection or listener.

    Think of it like a mailbox: - Server socket (LISTEN) = a mailbox accepting incoming letters - Established socket (ESTABLISHED) = an open letter being exchanged - Connecting socket (SYN_SENT) = you're writing a letter, waiting for reply

    Inspecting Sockets: The ss Command

    The ss (socket statistics) command supersedes the old netstat. It's faster and more powerful.

    Show All Listeners

    # Show all listening sockets (TCP and UDP)
ss -tuln

# output:
# Netid  State      Recv-Q Send-Q  Local Address:Port       Peer Address:Port Process
# tcp    LISTEN     0      128     0.0.0.0:22              0.0.0.0:*            users:(("sshd",pid=456))
# tcp    LISTEN     0      50      127.0.0.1:5432          0.0.0.0:*            users:(("postgres",pid=789))
# tcp    LISTEN     0      511     0.0.0.0:80              0.0.0.0:*            users:(("nginx",pid=1234))
# udp    UNCONN     0      0       0.0.0.0:53              0.0.0.0:*            users:(("systemd-resolve",pid=567))

    Flag explanations:

    • -t = TCP sockets
    • -u = UDP sockets
    • -l = listening sockets only
    • -n = numeric addresses (don't resolve names to avoid DNS lookups)

    Columns:

    • Recv-Q = bytes queued for the application to read (should be small)
    • Send-Q = bytes queued in the TCP send buffer (normal varies)
    • Local Address:Port = which interface and port this is bound to
    • Peer Address:Port = remote address (0.0.0.0 means listening to all)

    Show Established Connections

    # All established sockets
ss -tn state established

# output:
# Netid  State      Recv-Q Send-Q  Local Address:Port       Peer Address:Port
# tcp    ESTAB      0      0       192.168.1.100:443       203.0.113.50:52344
# tcp    ESTAB      0      0       192.168.1.100:5432      10.0.0.50:42891

    Count Connections by State

    # How many connections in each state?
ss -tn | awk '{print $2}' | sort | uniq -c

# output:
#      1 State
#     42 ESTAB
#     12 TIME_WAIT
#      3 LISTEN
#      1 SYN_RECV

    This shows you have 42 active connections, 12 that are closing (TIME_WAIT), 3 listeners, etc.

    Understanding Socket States

    State Meaning Normal Duration If Stuck = Problem
    LISTEN Waiting for connections Until service stops Service not running
    SYN_SENT Initiating connection < 1 second Remote not responding
    SYN_RECV Received SYN, not yet accepted < 1 second Application not accepting
    ESTAB Connection active Minutes to hours Data flowing
    FIN_WAIT_1 We sent FIN, waiting for ack < 1 second Remote not closing
    FIN_WAIT_2 We acked their FIN, waiting < 1 second Remote not responding
    TIME_WAIT Waiting before cleanup Default 60 seconds Normal, but if thousands stuck = problem
    CLOSE_WAIT Remote closed, we haven't < 1 second Application leak (not closing sockets)

    Critical fact: If you see thousands of CLOSE_WAIT sockets, your application is leaking connections — it's not properly closing them.

    Finding Which Process Owns a Socket

    # Show process names for each socket
ss -tulnp | grep 5432

# output:
# tcp  LISTEN  0  50  127.0.0.1:5432  0.0.0.0:*  users:(("postgres",pid=789,fd=5))

    Or if you know the port:

    # Which process is listening on port 8080?
lsof -i :8080

# output:
# COMMAND  PID  USER  FD  TYPE DEVICE          SIZE/OFF NODE NAME
# python  1234  app   3u  IPv4 0x12345678          0t0  TCP localhost:8080 (LISTEN)

    0.5 Firewalls: iptables and nftables

    What Is a Firewall Rule?

    A firewall rule is a kernel-level filter: "For packets matching X properties, perform Y action (ACCEPT, DROP, REJECT, etc.)".

    Linux has two firewall subsystems:

    1. iptables – older, still widely used
    2. nftables – modern replacement, but iptables still dominates

    iptables Basics

    List All Rules

    # Show all rules in human-readable form
sudo iptables -L

# or more verbose
sudo iptables -L -v

# Show raw format (useful for scripts)
sudo iptables -S

    Basic Rule Structure

    # Default policy: if no rule matches, DROP incoming packets
sudo iptables -P INPUT DROP

# Allow established connections
sudo iptables -A INPUT -m state --state ESTABLISHED,RELATED -j ACCEPT

# Allow SSH (port 22)
sudo iptables -A INPUT -p tcp --dport 22 -j ACCEPT

# Allow HTTP/HTTPS (ports 80, 443)
sudo iptables -A INPUT -p tcp --dport 80 -j ACCEPT
sudo iptables -A INPUT -p tcp --dport 443 -j ACCEPT

# Allow ICMP (ping)
sudo iptables -A INPUT -p icmp -j ACCEPT

# Allow localhost
sudo iptables -A INPUT -i lo -j ACCEPT

# Log dropped packets (for debugging)
sudo iptables -A INPUT -j LOG --log-prefix "Dropped: " --log-level 7

# Default policy: drop anything not explicitly allowed
sudo iptables -P INPUT DROP

    Flags Explained

    • -A = append rule to chain
    • -I = insert at beginning
    • -D = delete rule
    • -P = set default policy
    • -p = protocol (tcp, udp, icmp)
    • --dport = destination port
    • -i = incoming interface
    • -j = target/action (ACCEPT, DROP, REJECT, LOG)
    • -m state = match connection state

    Practical Example: Secure Web Server

    # Flush existing rules (start clean)
sudo iptables -F
sudo iptables -X  # delete custom chains

# Default: deny all incoming
sudo iptables -P INPUT DROP
sudo iptables -P FORWARD DROP
sudo iptables -P OUTPUT ACCEPT

# Allow loopback (needed for localhost services)
sudo iptables -A INPUT -i lo -j ACCEPT

# Allow established connections
sudo iptables -A INPUT -m state --state ESTABLISHED,RELATED -j ACCEPT

# Allow SSH (from anywhere — change to restrict)
sudo iptables -A INPUT -p tcp --dport 22 -j ACCEPT

# Allow HTTP
sudo iptables -A INPUT -p tcp --dport 80 -j ACCEPT

# Allow HTTPS
sudo iptables -A INPUT -p tcp --dport 443 -j ACCEPT

# Verify
sudo iptables -L -v

    Making iptables Persistent

    Rules are temporary (lost on reboot). To persist:

    On Ubuntu/Debian: 

    sudo apt-get install iptables-persistent
sudo iptables-save | sudo tee /etc/iptables/rules.v4

    On RHEL/CentOS: 

    sudo systemctl enable iptables
sudo systemctl restart iptables

    nftables: The Modern Alternative

    nftables is the successor, with simpler syntax:

    # List rules
sudo nft list ruleset

# Add a simple rule
sudo nft add rule inet filter input tcp dport 22 accept

    However, iptables is still ubiquitous. Learn both, but prioritize iptables for production systems.

    0.6 Packet Inspection: tcpdump and Wireshark

    Why Capture Packets?

    When a connection mysteriously fails, the only ground truth is what packets actually crossed the network. Logs can lie, but packets don't.

    Use packet capture to: - Verify that traffic reaches the host (or diagnose why it doesn't) - Inspect protocol negotiation (TLS handshake, HTTP headers) - Identify duplicate packets or out-of-order delivery - Find where connections are being reset

    tcpdump Basics

    # Capture packets on eth0 and print to screen
sudo tcpdump -i eth0

# Capture only HTTP traffic (port 80)
sudo tcpdump -i eth0 port 80

# Capture only HTTPS (port 443)
sudo tcpdump -i eth0 port 443

# Capture traffic to/from a specific host
sudo tcpdump -i eth0 host 192.168.1.100

# Capture only outgoing traffic (-i eth0 src 192.168.1.100)
sudo tcpdump -i eth0 src 192.168.1.100

# Capture in binary format (for Wireshark)
sudo tcpdump -i eth0 -w /tmp/capture.pcap port 443

# Limit to first 100 packets
sudo tcpdump -i eth0 -c 100

# Show packet contents (be careful, will show passwords!)
sudo tcpdump -i eth0 -A port 80

    Network Namespace Inspection

    Containers and Kubernetes pods use network namespaces for isolation:

    # List namespaces

    0.8 Best Practices & Troubleshooting

    Best Practices

    Best Practices: Linux Networking

    1. Use ip and ss, not ifconfig or netstat – They are faster and more complete.
    2. Capture packets on the server side – Client captures often miss the problem.
    3. Comment iptables rules – Future you (and your team) will thank you.
    4. Test routes locally before enabling – Use a test network interface.
    5. Use network namespaces for testing – Avoid breaking production.
    6. Automate with Ansible/Terraform – Manual ip commands are error-prone.
    7. Monitor packet drops – A silent ring-buffer overflow can tank performance.

    Common Troubleshooting Scenarios

    Scenario 1: Application Can't Reach Database

    # 1. Check if database service is listening
ss -tulnp | grep 5432

# 2. If yes, check if route exists
ip route show | grep database_subnet

# 3. If yes, check firewall
sudo iptables -L | grep 5432

# 4. If still blocked, capture packets
sudo tcpdump -i eth0 host database_ip -w /tmp/db.pcap

    Scenario 2: Port Is Listening but Connections Fail

    # Check socket state
ss -tnp | grep :8080

# Check how many connections are in CLOSE_WAIT (application leak?)
ss -tn | grep CLOSE_WAIT | wc -l

# Check if application is accepting
lsof -i :8080

# Monitor connections in real-time
watch -n 1 'ss -tn state established | wc -l'

    Scenario 3: Random Connection Drops

    # Check for packet loss on the wire
sudo tcpdump -i eth0 -c 1000 > /tmp/packets.txt
# Count retransmissions
grep "retransmit" /tmp/packets.txt

# Check ring buffer overflow
sudo ethtool -S eth0 | grep -i "rx.*error\|drop"

# If overflowing, increase buffer
sudo ethtool -G eth0 rx 4096

    💡 Core Takeaways

    ✅ Remember this: Most network problems are solved not by reading code, but by inspecting what the kernel and hardware are actually doing using ip, ss, and tcpdump.

    • Know your tools cold. Muscle memory matters at 3 AM when the API is down.
    • Interfaces and routes are foundational. If traffic doesn't reach the host or doesn't leave it, the app is blameless.
    • Socket states tell the full story. CLOSE_WAIT means applications leak; TIME_WAIT is normal.
    • Packet capture is the ultimate truth. When everything else is unclear, tcpdump never lies.
    • Firewall rules are evaluated in order. A single DROP rule before ACCEPT rules silently blocks traffic.
    • Persistent configuration matters. Manual ip commands vanish on reboot; automate with Ansible/Terraform.

    🧪 Hands-On Exercise

    Task: Diagnose why a local Flask API cannot be reached from a remote client.

    Scenario: You have a Flask app running on 127.0.0.1:5000 on a Linux server. A remote client at 192.168.1.50 attempts to connect to 192.168.1.100:5000 but gets "Connection refused".

    Step-by-step instructions:

    1. Check if Flask is actually listening: 

      ss -tulnp | grep 5000
      Result: You notice Flask is bound to 127.0.0.1:5000, not 0.0.0.0:5000. Issue found: It's only listening on localhost.

    2. Verify the application configuration (code change needed, not network): 

      # Wrong:
app.run(host='127.0.0.1', port=5000)

# Correct:
app.run(host='0.0.0.0', port=5000)

    3. Restart Flask and verify: 

      ss -tulnp | grep 5000
# Now shows: 0.0.0.0:5000

    4. From the remote client, test: 

      curl http://192.168.1.100:5000/
# Success!

    5. Capture and observe the traffic: 

      # On server:
sudo tcpdump -i eth0 port 5000 -c 10

# On client (in another terminal):
curl http://192.168.1.100:5000/

# Observe SYN, SYN-ACK, ACK in the capture

    Expected Output (before fix): 

    Client → Server: SYN (trying to connect)
Server: No response (port 5000 not listening on 0.0.0.0, only on 127.0.0.1)
Client: Retries, then timeout

    Expected Output (after fix): 

    Client → Server: SYN
Server → Client: SYN-ACK
Client → Server: ACK (connection established)
HTTP GET request from client
HTTP 200 response from Flask

    Reflection Question: If the Flask app was bound to 0.0.0.0:5000 but still didn't respond, what would be your next debugging step? (Answer: Check firewall rules with sudo iptables -L to see if port 5000 is blocked.)

    ❓ Review Questions

    1. What command shows all listening sockets with process names?
    2. How do you add a second IP address to interface eth0 temporarily?
    3. If ss -tn shows thousands of CLOSE_WAIT sockets, what is the likely problem?
    4. What does the routing table do, and how is it used when sending a packet to 8.8.8.8?
    5. Why is tcpdump on the server more useful than tcpdump on the client?
    6. What's the difference between iptables -A and iptables -I?
    7. If a rule like iptables -A INPUT -j DROP is placed before an ACCEPT rule, what happens?

    Answers:

    Click to reveal answers

    1. ss -tulnp or ss -tulnp | grep LISTEN

    2. sudo ip addr add 192.168.1.50/24 dev eth0 (or other CIDR). Remove with sudo ip addr del ...

    3. The application is not properly closing sockets — it's a connection leak. The application may have a bug or resource exhaustion.

    4. The routing table is a list of rules: "To reach network A, use gateway G via interface I". When sending to 8.8.8.8, the kernel searches for matching rules (longest prefix wins) and forwards packets accordingly. If no specific rule matches, the default gateway is used.

    5. The server capture shows both directions of traffic (arriving and leaving), whereas the client only sees its own traffic. Server-side captures reveal whether the server received the packet or a firewall dropped it.

    6. -A appends the rule to the end of the chain; -I inserts it at the beginning. Rule order matters because evaluation stops at the first match.

    7. The DROP rule will match everything, and the chain stops there. The later ACCEPT rule is unreachable. Always put more-specific rules before more-general ones.

    ⚠️ Common Exam / Interview Questions

    • "Which command would you use to find which process is listening on port 3000?"
      Answer: ss -tulnp | grep 3000 or lsof -i :3000

    • "Your API server is running on 0.0.0.0:8080 but clients can't reach it. How do you debug?"
      Answer: Check routes (ip route show), firewall (sudo iptables -L), and packet capture (sudo tcpdump -i eth0 port 8080).

    • "Explain the difference between ESTABLISHED and CLOSE_WAIT socket states."
      Answer: ESTABLISHED = connection active and healthy. CLOSE_WAIT = remote side closed, but application hasn't closed yet. Many CLOSE_WAIT = app bug.

    • "You accidentally deleted the default route on a remote server. How do recovery without physical access?"
      Answer: You can't (that's why you should always test locally first). Prevention: use configuration management to define routes persistently.

    • "Why should you prefer ip and ss over ifconfig and netstat?"
      Answer: ip/ss are faster (don't parse /proc), support full IPv6, handle virtual interfaces better, and have consistent syntax.

    Routing Table

    Linux maintains a routing table that decides where packets go.

    $ ip route show

default via 192.168.1.1 dev eth0 proto dhcp metric 100
192.168.1.0/24 dev eth0 proto kernel scope link src 192.168.1.100

    The default route handles traffic to any address not covered by a more specific route. You can add, modify or delete routes with ip route add/del.

    Socket States & Connections

    The ss command displays socket information much faster than the legacy netstat. It shows TCP/UDP listeners, established connections, and statistics.

    $ ss -tuln
Netid  State      Recv-Q Send-Q Local Address:Port               Peer Address:Port
tcp    LISTEN     0      128      0.0.0.0:22                        0.0.0.0:*
tcp    ESTAB      0      0        192.168.1.100:443                203.0.113.5:52344

    Filter by state: ss -tn state established shows only active TCP connections.

    Namespaces and Virtual Devices

    Containers and network virtualization use namespaces to provide isolated network stacks. The ip netns command lets you inspect and run commands inside a namespace.

    Firewalls (iptables/nftables)

    Linux uses iptables or nftables to filter packets. A basic rule set can block, allow or log traffic. We will cover the most common patterns below.

    Common Mistakes & Pitfalls

    Mistake: Forgetting to bring interface UP

    A new interface created with ip link add ... will be DOWN by default. You must ip link set dev eth1 up or you will see no traffic.

    Pitfall: Overwriting iptables chains

    Running iptables -F without understanding the default policy can lock you out of a remote host. Always check iptables -L first.

    Misreading CIDR notation

    192.168.1.0/24 includes addresses .0–.255 — the .0 network address and .255 broadcast. Don’t assign them to hosts.

    Real-World Use Cases

    1. Post-deployment connectivity check: After deploying a new service, SSH into the host, run ss -tan | grep LISTEN, and verify the port is bound.
    2. Firewall troubleshooting: A web app suddenly returns 403. Use sudo tcpdump -ni eth0 port 443 to see if packets arrive; then inspect iptables -L for unwanted drop rules.
    3. Performance optimization: High packet drop on 10GbE interface? ethtool -S eth0 shows ring buffer overflow counters; increase rx/tx buffer sizes with ethtool -G.
    4. Container networking: Diagnose Kubernetes pod network by entering the pod’s network namespace and running ip a / ss.
