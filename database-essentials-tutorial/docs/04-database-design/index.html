    Introduction & Core Principles

    Why Database Design Matters

    Bad design costs: - Hours debugging data inconsistencies - Millions of dollars in lost data - Months of refactoring - Career damage from production outages

    Good design delivers: - Fast, reliable systems - Consistent data - Easy maintenance - Confident deployments

    The Golden Rules

    Rule 1: Start normalized, denormalize only when measured

    Many engineers optimize prematurely, adding complexity they don't need. Normalize first, profile to find bottlenecks, then selectively denormalize.

    Rule 2: Understand your access patterns

    Different data needs different designs: - User authentication → Normalized, ACID guaranteed - Analytics → Denormalized, high-write volume - Product catalog → Flexible schema, reads optimized

    Rule 3: Let the database enforce constraints

    • Foreign keys prevent orphaned data
    • Check constraints prevent invalid data
    • Unique constraints prevent duplicates
    • NOT NULL constraints prevent missing data

    Normalization: Data Integrity

    What is Normalization?

    Normalization is the process of organizing data to eliminate redundancy and prevent inconsistencies.

    The Problem Without Normalization

    -- BAD: Highly redundant
CREATE TABLE orders (
    id SERIAL PRIMARY KEY,
    user_id INTEGER,
    user_email VARCHAR(255),      -- Redundant: stored in users table
    user_name VARCHAR(255),       -- Redundant: stored in users table
    user_phone VARCHAR(20),       -- Redundant: stored in users table
    product_id INTEGER,
    product_name VARCHAR(255),    -- Redundant
    product_price DECIMAL(10,2),  -- Redundant
    total DECIMAL(10,2)
);

-- Problems:
-- 1. Update user email: Must update in users table AND all their orders
-- 2. Risk: User has 2 different emails in different orders (data inconsistency)
-- 3. Storage: Same data repeated millions of times
-- 4. Queries: Harder to maintain, slower to update

    The Solution: Normalized Design

    -- GOOD: Properly normalized
CREATE TABLE users (
    id SERIAL PRIMARY KEY,
    email VARCHAR(255) UNIQUE NOT NULL,
    full_name VARCHAR(255) NOT NULL,
    phone VARCHAR(20),
    created_at TIMESTAMP DEFAULT NOW()
);

CREATE TABLE products (
    id SERIAL PRIMARY KEY,
    name VARCHAR(255) NOT NULL,
    price DECIMAL(10,2) NOT NULL,
    sku VARCHAR(50) UNIQUE NOT NULL
);

CREATE TABLE orders (
    id SERIAL PRIMARY KEY,
    user_id INTEGER NOT NULL REFERENCES users(id),
    created_at TIMESTAMP DEFAULT NOW()
);

CREATE TABLE order_items (
    id SERIAL PRIMARY KEY,
    order_id INTEGER NOT NULL REFERENCES orders(id) ON DELETE CASCADE,
    product_id INTEGER NOT NULL REFERENCES products(id),
    quantity INTEGER NOT NULL,
    price_at_purchase DECIMAL(10,2) NOT NULL  -- Snapshot of price
);

-- Benefits:
-- 1. Single source of truth: User email stored once
-- 2. Atomic updates: Update email, affects all orders automatically (via join)
-- 3. Space efficient: No duplication
-- 4. Consistent: Impossible for user to have 2 different emails

    Normalization Forms Explained

    1NF: First Normal Form - No Repeating Groups

    Atomic values only. No arrays or comma-separated strings in columns.

    -- BAD: Violates 1NF
CREATE TABLE users (
    id SERIAL PRIMARY KEY,
    email VARCHAR(255),
    phone_numbers VARCHAR(255)  -- "555-1111, 555-2222, 555-3333"
);

-- Problems:
-- - Can't query "find users with phone 555-1111"
-- - Hard to add/remove phone numbers
-- - Parsing strings in SQL is slow
-- - Unlimited scalability issues

-- GOOD: 1NF compliant
CREATE TABLE users (
    id SERIAL PRIMARY KEY,
    email VARCHAR(255)
);

CREATE TABLE user_phones (
    id SERIAL PRIMARY KEY,
    user_id INTEGER NOT NULL REFERENCES users(id) ON DELETE CASCADE,
    phone_number VARCHAR(20) NOT NULL,
    UNIQUE(user_id, phone_number)  -- No duplicates per user
);

-- Benefits:
-- - Query: SELECT * FROM users WHERE id IN (SELECT user_id FROM user_phones WHERE phone_number = '555-1111')
-- - Easy to add/remove phones
-- - Database enforces constraints
-- - Handles unlimited phones

    2NF: Second Normal Form - No Partial Dependencies

    Non-key columns must depend on the entire primary key, not just part of it.

    -- BAD: Violates 2NF
CREATE TABLE order_items (
    order_id INTEGER,
    product_id INTEGER,
    product_name VARCHAR(255),      -- Depends on product_id ONLY
    product_sku VARCHAR(50),        -- Depends on product_id ONLY
    quantity INTEGER,
    PRIMARY KEY (order_id, product_id)
);

-- The problem:
-- product_name depends on product_id (part of key)
-- NOT on the whole key (order_id, product_id)
-- Update product name: must update in ALL orders

-- GOOD: 2NF compliant
CREATE TABLE products (
    id SERIAL PRIMARY KEY,
    name VARCHAR(255) NOT NULL,
    sku VARCHAR(50) NOT NULL UNIQUE
);

CREATE TABLE order_items (
    order_id INTEGER NOT NULL,
    product_id INTEGER NOT NULL REFERENCES products(id),
    quantity INTEGER NOT NULL,
    PRIMARY KEY (order_id, product_id)
);

-- Benefits:
-- - Product info in one place
-- - Update product name once, everywhere correct
-- - No data inconsistency

    3NF: Third Normal Form - No Transitive Dependencies

    Non-key columns must depend on the primary key, not on other non-key columns.

    -- BAD: Violates 3NF
CREATE TABLE orders (
    id SERIAL PRIMARY KEY,
    user_id INTEGER NOT NULL,
    user_email VARCHAR(255),       -- Depends on user_id
    user_city VARCHAR(100),        -- Depends on user_id
    user_country VARCHAR(100),     -- Depends on user_id
    total DECIMAL(10,2)
);

-- The problem:
-- user_email, user_city, user_country don't depend on order id
-- They depend on user_id (transitive dependency)
-- Update user city: must update in ALL orders (inconsistency risk)

-- GOOD: 3NF compliant
CREATE TABLE users (
    id SERIAL PRIMARY KEY,
    email VARCHAR(255),
    city VARCHAR(100),
    country VARCHAR(100)
);

CREATE TABLE orders (
    id SERIAL PRIMARY KEY,
    user_id INTEGER NOT NULL REFERENCES users(id),
    total DECIMAL(10,2)
);

-- Benefits:
-- - User info in one place
-- - Update user city once, affects all their orders (via join)
-- - Single source of truth
-- - Easier to query and maintain

    When to Stop Normalizing

    3NF is usually the sweet spot. Beyond this (BCNF, 4NF) introduces complexity most applications don't need.

    -- GOOD: Stop at 3NF
-- Most productions databases are 3NF normalized
-- Simple to understand, maintain, and query

-- 4NF+ introduces:
-- - More tables (more joins)
-- - More complex queries
-- - Minimal real-world benefit for most applications

    Denormalization: Performance

    What is Denormalization?

    Denormalization is strategic redundancy. You duplicate data to improve read performance, accepting the trade-off of update complexity.

    When to Denormalize

    Only denormalize when ALL of these are true:

    1. Measured bottleneck - Profiling shows joins are slow
    2. Read-heavy workload - Reads >> writes
    3. Caching insufficient - Redis/Memcached doesn't solve it
    4. Worth the complexity - Performance gain justifies update logic

    Denormalization Example: E-commerce Orders

    Normalized Approach (Many joins)

    -- 4 tables, 3 joins needed
SELECT 
    o.id,
    o.created_at,
    u.email,
    u.full_name,
    p.name as product_name,
    oi.quantity,
    oi.unit_price
FROM orders o
JOIN users u ON o.user_id = u.id
JOIN order_items oi ON o.id = oi.order_id
JOIN products p ON oi.product_id = p.id
WHERE o.id = 123;

-- Performance: ~25ms per query (3 joins)
-- With 1000 concurrent requests: ~25 seconds overhead

    Denormalized Approach (No joins)

    -- Store snapshot of user/product data at order time
CREATE TABLE orders (
    id SERIAL PRIMARY KEY,
    user_id INTEGER REFERENCES users(id),
    user_email VARCHAR(255),      -- Snapshot at order time
    user_full_name VARCHAR(255),  -- Snapshot
    created_at TIMESTAMP,
    total DECIMAL(10,2)
);

CREATE TABLE order_items (
    id SERIAL PRIMARY KEY,
    order_id INTEGER REFERENCES orders(id),
    product_id INTEGER REFERENCES products(id),
    product_name VARCHAR(255),    -- Snapshot at purchase
    quantity INTEGER,
    price_at_purchase DECIMAL(10,2)  -- Snapshot (important!)
);

-- Single query, no joins
SELECT * FROM orders WHERE id = 123;
SELECT * FROM order_items WHERE order_id = 123;

-- Performance: ~10ms total (no joins)
-- 60% faster, much simpler queries

    Managing Denormalized Updates

    Key insight: Denormalized fields are often snapshots, not live copies.

    # When user updates email, should order show old OR new email?
# Answer: OLD EMAIL (historical accuracy)
# An order shows what the user's email WAS at purchase time

def update_user_email(user_id: int, new_email: str):
    """Update user email. Orders keep historical email."""
    user = User.query.get(user_id)
    user.email = new_email
    db.session.commit()

    # Don't update orders—they're historical records
    # Orders should show the email at purchase time

    # If you need current email with orders:
    # SELECT * FROM orders JOIN users USING(user_id) WHERE orders.id = 123

    Alternative: Live denormalized data

    def update_user_email(user_id: int, new_email: str):
    """Update user email everywhere."""
    user = User.query.get(user_id)
    user.email = new_email
    db.session.commit()

    # Update denormalized copies (if needed)
    Order.query.filter_by(user_id=user_id).update(
        {'user_email': new_email}
    )
    db.session.commit()

    # Trade-off: Extra update, but queries see current email
    # Usually NOT worth it—snapshots are better

    Denormalization Strategies

    Strategy 1: Summary fields 

    -- Instead of: SELECT COUNT(*) FROM comments WHERE post_id = 1
-- Store summary
CREATE TABLE posts (
    id SERIAL PRIMARY KEY,
    title VARCHAR(500),
    comment_count INTEGER DEFAULT 0
);

-- Update with triggers
CREATE OR REPLACE FUNCTION update_post_comment_count()
RETURNS TRIGGER AS $$
BEGIN
    UPDATE posts SET comment_count = comment_count + 1
    WHERE id = NEW.post_id;
    RETURN NEW;
END;
$$ LANGUAGE plpgsql;

CREATE TRIGGER after_comment_insert
AFTER INSERT ON comments
FOR EACH ROW EXECUTE FUNCTION update_post_comment_count();

    Strategy 2: Computed columns 

    -- PostgreSQL 12+: Generated columns
CREATE TABLE line_items (
    id SERIAL PRIMARY KEY,
    quantity INTEGER,
    unit_price DECIMAL(10,2),
    total DECIMAL(10,2) GENERATED ALWAYS AS (quantity * unit_price) STORED
);

    Strategy 3: Caching layer 

    # Cache instead of denormalizing
def get_user_post_count(user_id):
    cache_key = f'user:{user_id}:post_count'

    count = redis.get(cache_key)
    if count:
        return int(count)

    count = Post.query.filter_by(user_id=user_id).count()
    redis.set(cache_key, count, ex=300)  # Cache 5 minutes

    return count

    Entity Relationships

    One-to-Many (1:N)

    Definition: One parent has many children. Each child has exactly one parent.

    Examples: - User has many Posts - Post has many Comments - Company has many Employees

    CREATE TABLE users (
    id SERIAL PRIMARY KEY,
    email VARCHAR(255) UNIQUE NOT NULL
);

CREATE TABLE posts (
    id SERIAL PRIMARY KEY,
    user_id INTEGER NOT NULL REFERENCES users(id) ON DELETE CASCADE,
    title VARCHAR(500),
    content TEXT,
    created_at TIMESTAMP DEFAULT NOW()
);

-- Queries
-- Get all posts by user
SELECT * FROM posts WHERE user_id = 123;

-- Get user with posts
SELECT u.*, COUNT(p.id) as post_count
FROM users u
LEFT JOIN posts p ON u.id = p.user_id
WHERE u.id = 123
GROUP BY u.id;

    SQLAlchemy: 

    class User(db.Model):
    id = db.Column(db.Integer, primary_key=True)
    email = db.Column(db.String(255), unique=True, nullable=False)
    posts = db.relationship('Post', backref='user', lazy='dynamic')

class Post(db.Model):
    id = db.Column(db.Integer, primary_key=True)
    user_id = db.Column(db.Integer, db.ForeignKey('users.id'), nullable=False)
    title = db.Column(db.String(500))
    content = db.Column(db.Text)

# Usage
user = User.query.get(1)
user_posts = user.posts.all()  # All posts by user

post = Post.query.get(1)
post_author = post.user  # Access via backref

    Many-to-Many (M:N)

    Definition: Both sides can have many. Implemented with a junction table.

    Examples: - Posts have many Tags - Students enroll in many Courses - Users follow many Users

    CREATE TABLE posts (
    id SERIAL PRIMARY KEY,
    title VARCHAR(500)
);

CREATE TABLE tags (
    id SERIAL PRIMARY KEY,
    name VARCHAR(50) UNIQUE NOT NULL
);

-- Junction table
CREATE TABLE post_tags (
    post_id INTEGER NOT NULL REFERENCES posts(id) ON DELETE CASCADE,
    tag_id INTEGER NOT NULL REFERENCES tags(id) ON DELETE CASCADE,
    PRIMARY KEY (post_id, tag_id)
);

-- Queries
-- Get posts with tag "python"
SELECT p.* FROM posts p
JOIN post_tags pt ON p.id = pt.post_id
JOIN tags t ON pt.tag_id = t.id
WHERE t.name = 'python';

-- Get tags for a post
SELECT t.* FROM tags t
JOIN post_tags pt ON t.id = pt.tag_id
WHERE pt.post_id = 456;

    SQLAlchemy: 

    post_tags = db.Table('post_tags',
    db.Column('post_id', db.Integer, db.ForeignKey('posts.id'), primary_key=True),
    db.Column('tag_id', db.Integer, db.ForeignKey('tags.id'), primary_key=True)
)

class Post(db.Model):
    id = db.Column(db.Integer, primary_key=True)
    title = db.Column(db.String(500))
    tags = db.relationship('Tag', secondary=post_tags, backref='posts')

class Tag(db.Model):
    id = db.Column(db.Integer, primary_key=True)
    name = db.Column(db.String(50), unique=True, nullable=False)

# Usage
post = Post.query.get(1)
post.tags  # All tags for this post

post.tags.append(Tag.query.filter_by(name='python').first())
db.session.commit()

    One-to-One (1:1)

    Definition: Each side has exactly one of the other. Rare in practice.

    Examples: - User has one Profile - Country has one Capital - Employee has one Passport

    CREATE TABLE users (
    id SERIAL PRIMARY KEY,
    email VARCHAR(255),
    created_at TIMESTAMP
);

-- Profile has same PK as user (enforces 1:1)
CREATE TABLE user_profiles (
    user_id INTEGER PRIMARY KEY REFERENCES users(id) ON DELETE CASCADE,
    bio TEXT,
    avatar_url VARCHAR(500),
    website VARCHAR(255)
);

-- Queries
SELECT u.*, up.bio, up.avatar_url
FROM users u
LEFT JOIN user_profiles up ON u.id = up.user_id
WHERE u.id = 123;

    SQLAlchemy: 

    class User(db.Model):
    id = db.Column(db.Integer, primary_key=True)
    email = db.Column(db.String(255))
    profile = db.relationship('UserProfile', backref='user', uselist=False)

class UserProfile(db.Model):
    user_id = db.Column(db.Integer, db.ForeignKey('users.id'), primary_key=True)
    bio = db.Column(db.Text)
    avatar_url = db.Column(db.String(500))

# Usage
user = User.query.get(1)
user.profile.bio  # Access profile

    Design Patterns

    Account System Pattern

    CREATE TABLE users (
    id SERIAL PRIMARY KEY,
    email VARCHAR(255) UNIQUE NOT NULL,
    password_hash VARCHAR(255) NOT NULL,
    created_at TIMESTAMP DEFAULT NOW()
);

CREATE TABLE user_profiles (
    user_id INTEGER PRIMARY KEY REFERENCES users(id),
    full_name VARCHAR(255),
    avatar_url VARCHAR(500)
);

CREATE TABLE user_settings (
    user_id INTEGER PRIMARY KEY REFERENCES users(id),
    theme VARCHAR(20) DEFAULT 'light',
    notifications_enabled BOOLEAN DEFAULT TRUE,
    language VARCHAR(10) DEFAULT 'en'
);

-- Why separate tables:
-- - Users: Authentication/core data
-- - Profiles: Optional user info (some users never fill)
-- - Settings: User preferences (can change frequently)
-- - Faster queries: Load only what you need

    Hierarchical Data Pattern

    -- Category hierarchy (parent-child)
CREATE TABLE categories (
    id SERIAL PRIMARY KEY,
    parent_id INTEGER REFERENCES categories(id),
    name VARCHAR(255),
    slug VARCHAR(255)
);

-- Example:
-- Electronics (id=1, parent=NULL)
#   Computers (id=2, parent=1)
#     Laptops (id=3, parent=2)
#     Desktops (id=4, parent=2)
#   Phones (id=5, parent=1)

-- Query: Get children of a category
SELECT * FROM categories WHERE parent_id = 1;

-- Query: Get path to root
WITH RECURSIVE path AS (
    SELECT id, parent_id, name, 0 as level
    FROM categories WHERE id = 3
    UNION ALL
    SELECT c.id, c.parent_id, c.name, path.level + 1
    FROM categories c
    JOIN path ON c.id = path.parent_id
)
SELECT * FROM path;

    Audit Log Pattern

    CREATE TABLE posts (
    id SERIAL PRIMARY KEY,
    title VARCHAR(500),
    content TEXT,
    created_at TIMESTAMP DEFAULT NOW(),
    updated_at TIMESTAMP DEFAULT NOW()
);

CREATE TABLE post_audit (
    id SERIAL PRIMARY KEY,
    post_id INTEGER NOT NULL REFERENCES posts(id) ON DELETE CASCADE,
    user_id INTEGER NOT NULL,
    action VARCHAR(20),  -- 'INSERT', 'UPDATE', 'DELETE'
    old_values JSONB,
    new_values JSONB,
    changed_at TIMESTAMP DEFAULT NOW()
);

-- Create audit trigger
CREATE OR REPLACE FUNCTION audit_post_changes()
RETURNS TRIGGER AS $$
BEGIN
    INSERT INTO post_audit (post_id, user_id, action, old_values, new_values)
    VALUES (
        COALESCE(NEW.id, OLD.id),
        current_user_id,
        TG_OP,
        to_jsonb(OLD),
        to_jsonb(NEW)
    );
    RETURN COALESCE(NEW, OLD);
END;
$$ LANGUAGE plpgsql;

CREATE TRIGGER post_audit_trigger
AFTER INSERT OR UPDATE OR DELETE ON posts
FOR EACH ROW EXECUTE FUNCTION audit_post_changes();

    Anti-Patterns to Avoid

    ❌ Anti-Pattern 1: God Table

    -- BAD: Everything crammed into one table
CREATE TABLE users (
    id SERIAL PRIMARY KEY,
    -- Authentication
    email VARCHAR(255) UNIQUE,
    password_hash VARCHAR(255),
    -- Profile
    first_name VARCHAR(100),
    last_name VARCHAR(100),
    bio TEXT,
    avatar_url VARCHAR(500),
    -- Settings
    theme VARCHAR(20),
    notifications_enabled BOOLEAN,
    language VARCHAR(10),
    -- Metadata
    created_at TIMESTAMP,
    updated_at TIMESTAMP,
    last_login TIMESTAMP,
    login_count INTEGER,
    -- More fields...
    -- ... 50 columns total
);

-- Problems:
-- - Query entire huge row even if needs just email
-- - Hard to NULL fields users don't fill
-- - Mixed concerns (auth, profile, settings in one table)
-- - Slow indexes on huge row

-- GOOD: Separate by concern
CREATE TABLE users (id, email, password_hash);
CREATE TABLE user_profiles (user_id, first_name, last_name, bio, avatar_url);
CREATE TABLE user_settings (user_id, theme, notifications_enabled, language);
CREATE TABLE user_metadata (user_id, created_at, updated_at, last_login, login_count);

    ❌ Anti-Pattern 2: EAV (Entity-Attribute-Value)

    -- BAD: Generic attribute storage
CREATE TABLE entity_attributes (
    entity_id INTEGER,
    attribute_name VARCHAR(100),
    attribute_value TEXT,
    PRIMARY KEY (entity_id, attribute_name)
);

-- Nightmare to query
SELECT * FROM entity_attributes
WHERE entity_id = 1 AND attribute_name = 'email';
-- vs normal: SELECT email FROM users WHERE id = 1;

-- Problems:
-- - No type safety (all values are TEXT)
-- - Complex queries
-- - Hard to validate
-- - Slow indexes
-- - Confusing to maintain

-- GOOD: Proper columns or JSONB
CREATE TABLE users (
    id SERIAL PRIMARY KEY,
    email VARCHAR(255),
    metadata JSONB  -- For truly flexible data
);

    ❌ Anti-Pattern 3: Surrogate Keys Without Natural Keys

    -- BAD: No constraints on real data
CREATE TABLE users (
    id SERIAL PRIMARY KEY,
    email VARCHAR(255),  -- No unique constraint!
    username VARCHAR(100)  -- No unique constraint!
);

-- Problems:
-- - Duplicate emails possible
-- - Impossible to prevent data corruption
-- - queries: WHERE id = 1 (must know ID)
-- - No business constraints

-- GOOD: Appropriate constraints
CREATE TABLE users (
    id SERIAL PRIMARY KEY,
    email VARCHAR(255) UNIQUE NOT NULL,
    username VARCHAR(100) UNIQUE NOT NULL,
    created_at TIMESTAMP DEFAULT NOW()
);

-- Or: Use Natural Key if better fit
CREATE TABLE countries (
    iso_code CHAR(2) PRIMARY KEY,  -- Natural key
    name VARCHAR(255) UNIQUE NOT NULL
);

    ❌ Anti-Pattern 4: Ignoring Cascade Behavior

    -- BAD: Orphaned children
CREATE TABLE orders (
    id SERIAL PRIMARY KEY,
    user_id INTEGER REFERENCES users(id)  -- No cascade
);

-- User deletes account → Orders stay in DB orphaned
-- Delete user manually? Forget → Data inconsistency

-- GOOD: Specify cascade behavior
CREATE TABLE orders (
    id SERIAL PRIMARY KEY,
    user_id INTEGER NOT NULL REFERENCES users(id) ON DELETE CASCADE
);
-- Delete user → All their orders deleted automatically, stays consistent

-- Other options:
-- ON DELETE SET NULL: orders.user_id becomes NULL
-- ON DELETE RESTRICT: Prevent delete if orders exist
-- ON DELETE SET DEFAULT: Set to default value

    Normalization eliminates redundancy and ensures consistency. Denormalization adds strategic redundancy for performance.

    Normalization (Relational Databases)

    Goal: Eliminate data redundancy and prevent inconsistencies

    Why it matters: 

    -- BAD: Redundant data
CREATE TABLE orders (
    id SERIAL PRIMARY KEY,
    user_id INTEGER,
    user_email VARCHAR(255),      -- Redundant (stored in users table)
    user_name VARCHAR(255),       -- Redundant (stored in users table)
    total DECIMAL(10, 2)
);

-- Problem: Update user email
UPDATE users SET email = 'newemail@example.com' WHERE id = 123;
-- But orders table still has old email!
-- Data inconsistency: user has 2 different emails

-- GOOD: Normalized
CREATE TABLE orders (
    id SERIAL PRIMARY KEY,
    user_id INTEGER REFERENCES users(id),  -- Reference, not copy
    total DECIMAL(10, 2)
);

-- Query still works:
SELECT o.*, u.email FROM orders o JOIN users u ON o.user_id = u.id;
-- Email always correct (fetched from users table)

    Normal Forms (what actually matters):

    1NF (First Normal Form): No repeating groups 

    -- BAD: Violates 1NF
CREATE TABLE users (
    id SERIAL PRIMARY KEY,
    email VARCHAR(255),
    phone_numbers VARCHAR(255)  -- "555-1234, 555-5678" (multiple values)
);

-- Problem:
-- Can't query "users with phone 555-1234"
-- Can't add third phone number
-- Parsing strings is slow and error-prone

-- GOOD: 1NF compliant
CREATE TABLE users (
    id SERIAL PRIMARY KEY,
    email VARCHAR(255)
);

CREATE TABLE user_phones (
    id SERIAL PRIMARY KEY,
    user_id INTEGER REFERENCES users(id),
    phone_number VARCHAR(20)
);

-- Now you can:
-- SELECT * FROM users WHERE id IN (SELECT user_id FROM user_phones WHERE phone_number = '555-1234');
-- Add unlimited phones
-- Query efficiently

    2NF (Second Normal Form): No partial dependencies 

    -- BAD: Violates 2NF
CREATE TABLE order_items (
    order_id INTEGER,
    product_id INTEGER,
    product_name VARCHAR(255),       -- Depends on product_id, not order
    product_price DECIMAL(10, 2),    -- Same issue
    quantity INTEGER,
    PRIMARY KEY (order_id, product_id)
);

-- Problem:
-- Update product name: must update in ALL orders that contain it
-- Data inconsistency risk

-- GOOD: 2NF compliant
CREATE TABLE products (
    id SERIAL PRIMARY KEY,
    name VARCHAR(255),
    price DECIMAL(10, 2)
);

CREATE TABLE order_items (
    order_id INTEGER,
    product_id INTEGER REFERENCES products(id),
    quantity INTEGER,
    PRIMARY KEY (order_id, product_id)
);

-- Benefits:
-- Product name in one place
-- Update once, everywhere correct

    3NF (Third Normal Form): No transitive dependencies 

    -- BAD: Violates 3NF
CREATE TABLE orders (
    id SERIAL PRIMARY KEY,
    user_id INTEGER,
    user_email VARCHAR(255),        -- Depends on user_id
    user_city VARCHAR(100),         -- Depends on user_id
    total DECIMAL(10, 2)
);

-- Problem: Non-key columns depend on non-key column (user_id)
-- Update user's city: must update in all their orders
-- Risk of inconsistency

-- GOOD: 3NF compliant
CREATE TABLE users (
    id SERIAL PRIMARY KEY,
    email VARCHAR(255),
    city VARCHAR(100)
);

CREATE TABLE orders (
    id SERIAL PRIMARY KEY,
    user_id INTEGER REFERENCES users(id),
    total DECIMAL(10, 2)
);

-- Benefits:
-- Update user once, affects all their orders automatically (via join)
-- Single source of truth for user data

    Production rule: Aim for 3NF by default. Denormalize only when profiling proves you need to.

    **2NF (Second Normal Form)**: No partial dependencies

-- BAD: Violates 2NF
CREATE TABLE order_items (
    order_id INTEGER,

    product_name VARCHAR(255),  -- Depends only on product_id
    quantity INTEGER,

);

-- GOOD: 2NF compliant
CREATE TABLE products (
    id SERIAL PRIMARY KEY,
    name VARCHAR(255)
);

CREATE TABLE order_items (
    order_id INTEGER,
    product_id INTEGER REFERENCES products(id),
    quantity INTEGER,
    PRIMARY KEY (order_id, product_id)

    3NF (Third Normal Form): No transitive dependencies 

    -- BAD: Violates 3NF
CREATE TABLE orders (
    id SERIAL PRIMARY KEY,
    user_id INTEGER,
    user_email VARCHAR(255),  -- Depends on user_id, not order id
    total DECIMAL(10, 2)

-- GOOD: 3NF compliant
CREATE TABLE users (

    Production rule: Aim for 3NF, denormalize only when performance requires it.

    Denormalization (Performance Optimization)

    The principle: Redundancy for speed, at the cost of consistency complexity.

    When to denormalize: - Read-heavy workloads - Data accessed frequently but changed rarely - Expensive joins - Queries require many joins across tables - Caching insufficient - Redis/Memcached not available or misses too often - Profiling shows problem - You measured and joins are actually slow

    When NOT to denormalize: - High write frequency - Updates must replicate to multiple places - Consistency critical - Stale data causes problems - Premature optimization - "Might be slow" is not a reason - Before measuring - Profile first, optimize second

    Example: E-commerce orders

    Normalized approach (multiple joins): 

    -- Get order with all details
-- Requires 4 tables and 3 joins
SELECT 
    o.id,
    o.created_at,
    u.email,                    -- From users table (JOIN 1)
    u.full_name,               -- From users table (JOIN 1)
    p.name as product_name,    -- From products table (JOIN 2)
    oi.quantity,               -- From order_items
    oi.unit_price,
    (oi.quantity * oi.unit_price) as subtotal
FROM orders o
JOIN users u ON o.user_id = u.id           -- JOIN 1
JOIN order_items oi ON o.id = oi.order_id  -- JOIN 2
JOIN products p ON oi.product_id = p.id    -- JOIN 3
WHERE o.id = 123;

-- With 1000 concurrent requests:
-- Each query does 3 joins = 3000 operations
-- Locks tables, slows down everything

    Performance analysis: - Scan orders: 10ms - Join users: 5ms - Join order_items: 5ms - Join products: 5ms - Total: 25ms per query - 1000 concurrent: 25,000ms overhead

    Denormalized approach (no joins): 

    -- Store snapshot of data in orders table
-- No joins needed
CREATE TABLE orders (
    id SERIAL PRIMARY KEY,
    user_id INTEGER REFERENCES users(id),
    user_email VARCHAR(255),       -- Snapshot at order time
    user_name VARCHAR(255),        -- Snapshot at order time
    total DECIMAL(10, 2),
    status VARCHAR(20),
    created_at TIMESTAMP
);

-- Store snapshot in order_items
CREATE TABLE order_items (
    id SERIAL PRIMARY KEY,
    order_id INTEGER REFERENCES orders(id),
    product_id INTEGER REFERENCES products(id),
    product_name VARCHAR(255),     -- Snapshot at purchase time
    product_sku VARCHAR(50),       -- Snapshot at purchase time
    quantity INTEGER,
    price_per_unit DECIMAL(10, 2), -- Snapshot (important for invoices)
    created_at TIMESTAMP
);

-- Query: No joins!
SELECT * FROM orders WHERE id = 123;
SELECT * FROM order_items WHERE order_id = 123;

-- Performance: 10ms + 5ms = 15ms (no join overhead)
-- 1000 concurrent: 15,000ms overhead (40% faster)

    Trade-off and management: 

    # When user updates email in users table
def update_user_email(user_id, new_email):
    # 1. Update primary source (users table)
    user = User.query.get(user_id)
    user.email = new_email
    db.session.commit()

    # 2. Update denormalized copies
    # Option A: Update all related orders (eventual consistency)
    Order.query.filter_by(user_id=user_id).update(
        {'user_email': new_email}
    )
    db.session.commit()

    # Option B: Don't update old orders (correct - historical data)
    # Current order shows old email (accurate for that time)

    # Option C: Invalidate cache (for read-only display)
    # redis.delete(f'user:profile:{user_id}')

    Key insight: Denormalization is not just copying data. It's storing snapshots of related data at a point in time. This is often correct—an order should show the price and product name at the time of order, not current values.

    user_email VARCHAR(255),  -- Denormalized
user_name VARCHAR(255),   -- Denormalized
total DECIMAL(10, 2),
created_at TIMESTAMP

    );

    CREATE TABLE order_items ( id SERIAL PRIMARY KEY, order_id INTEGER REFERENCES orders(id), product_id INTEGER REFERENCES products(id), product_name VARCHAR(255), -- Denormalized quantity INTEGER, price DECIMAL(10, 2) -- Snapshot of price at purchase time );

    -- Single query, no joins SELECT * FROM orders WHERE id = 123; SELECT * FROM order_items WHERE order_id = 123; 

    **Trade-off**: Faster reads, but must update denormalized data when source changes.

    Designing for Reads vs Writes

    Read-Heavy Systems

    Characteristics: - Social media feeds - News sites - Product catalogs

    Optimization strategies:

    1. Denormalize data 

      -- Store computed values
CREATE TABLE posts (
    id SERIAL PRIMARY KEY,
    title VARCHAR(500),
    comment_count INTEGER DEFAULT 0,  -- Denormalized
    like_count INTEGER DEFAULT 0,     -- Denormalized
    created_at TIMESTAMP
);

-- Update counts with triggers
CREATE OR REPLACE FUNCTION update_comment_count()
RETURNS TRIGGER AS $$
BEGIN
    UPDATE posts SET comment_count = comment_count + 1
    WHERE id = NEW.post_id;
    RETURN NEW;
END;
$$ LANGUAGE plpgsql;

CREATE TRIGGER increment_comment_count
AFTER INSERT ON comments
FOR EACH ROW EXECUTE FUNCTION update_comment_count();

    2. Add indexes aggressively 

      CREATE INDEX idx_posts_created_at ON posts(created_at);
CREATE INDEX idx_posts_user_id ON posts(user_id);
CREATE INDEX idx_posts_published ON posts(published) WHERE published = TRUE;

    3. Use caching 

      @cache.memoize(timeout=300)
def get_popular_posts():
    return Post.query.filter_by(published=True)\
        .order_by(Post.like_count.desc())\
        .limit(10).all()

    Write-Heavy Systems

    Characteristics: - Logging systems - Analytics ingestion - IoT data collection

    Optimization strategies:

    1. Minimize indexes 

      -- Only essential indexes
CREATE TABLE logs (
    id BIGSERIAL PRIMARY KEY,
    level VARCHAR(20),
    message TEXT,
    timestamp TIMESTAMP DEFAULT NOW()
);

-- Only index timestamp for time-range queries
CREATE INDEX idx_logs_timestamp ON logs(timestamp);

    2. Use batch inserts 

      # BAD: Individual inserts
for log in logs:
    db.session.add(Log(**log))
    db.session.commit()  # Slow!

# GOOD: Batch insert
db.session.bulk_insert_mappings(Log, logs)
db.session.commit()  # Fast!

    3. Consider append-only design 

      -- Never UPDATE or DELETE, only INSERT
CREATE TABLE events (
    id BIGSERIAL PRIMARY KEY,
    event_type VARCHAR(50),
    user_id INTEGER,
    data JSONB,
    created_at TIMESTAMP DEFAULT NOW()
);

    Common Anti-Patterns

    Anti-Pattern 1: God Table

    -- BAD: Everything in one table
CREATE TABLE users (
    id SERIAL PRIMARY KEY,
    email VARCHAR(255),
    password_hash VARCHAR(255),
    -- Profile fields
    bio TEXT,
    avatar_url VARCHAR(500),
    -- Settings
    theme VARCHAR(20),
    notifications_enabled BOOLEAN,
    -- Metadata
    last_login TIMESTAMP,
    login_count INTEGER,
    -- ... 50 more columns
);

    Fix: Separate concerns 

    CREATE TABLE users (
    id SERIAL PRIMARY KEY,
    email VARCHAR(255),
    password_hash VARCHAR(255)
);

CREATE TABLE user_profiles (
    user_id INTEGER PRIMARY KEY REFERENCES users(id),
    bio TEXT,
    avatar_url VARCHAR(500)
);

CREATE TABLE user_settings (
    user_id INTEGER PRIMARY KEY REFERENCES users(id),
    theme VARCHAR(20),
    notifications_enabled BOOLEAN
);

    Anti-Pattern 2: EAV (Entity-Attribute-Value)

    -- BAD: Generic attribute table
CREATE TABLE entity_attributes (
    entity_id INTEGER,
    attribute_name VARCHAR(100),
    attribute_value TEXT
);

-- Nightmare to query
SELECT * FROM entity_attributes
WHERE entity_id = 1 AND attribute_name = 'email';

    Fix: Use proper columns or JSONB 

    -- Option 1: Proper columns
CREATE TABLE users (
    id SERIAL PRIMARY KEY,
    email VARCHAR(255),
    full_name VARCHAR(255)
);

-- Option 2: JSONB for flexible data
CREATE TABLE users (
    id SERIAL PRIMARY KEY,
    email VARCHAR(255),
    metadata JSONB
);

    Anti-Pattern 3: Polymorphic Associations

    -- BAD: Generic foreign key
CREATE TABLE comments (
    id SERIAL PRIMARY KEY,
    commentable_type VARCHAR(50),  -- 'Post' or 'Photo'
    commentable_id INTEGER,        -- ID of post or photo
    content TEXT
);

-- Can't enforce foreign key constraint
-- Can't join efficiently

    Fix: Separate tables or use inheritance 

    -- Option 1: Separate tables
CREATE TABLE post_comments (
    id SERIAL PRIMARY KEY,
    post_id INTEGER REFERENCES posts(id),
    content TEXT
);

CREATE TABLE photo_comments (
    id SERIAL PRIMARY KEY,
    photo_id INTEGER REFERENCES photos(id),
    content TEXT
);

-- Option 2: Nullable foreign keys
CREATE TABLE comments (
    id SERIAL PRIMARY KEY,
    post_id INTEGER REFERENCES posts(id),
    photo_id INTEGER REFERENCES photos(id),
    content TEXT,
    CHECK (
        (post_id IS NOT NULL AND photo_id IS NULL) OR
        (post_id IS NULL AND photo_id IS NOT NULL)
    )
);

    Anti-Pattern 4: Premature Optimization

    # BAD: Over-engineering before measuring
class UserRepository:
    def get_user(self, user_id):
        # Complex caching logic
        # Multiple cache layers
        # Unnecessary complexity
        pass

    Fix: Start simple, optimize when needed 

    # GOOD: Simple first
class UserRepository:
    def get_user(self, user_id):
        return User.query.get(user_id)

    Real-World Example: Blog Platform

    -- Users
CREATE TABLE users (
    id SERIAL PRIMARY KEY,
    email VARCHAR(255) UNIQUE NOT NULL,
    password_hash VARCHAR(255) NOT NULL,
    full_name VARCHAR(255) NOT NULL,
    created_at TIMESTAMP DEFAULT NOW()
);

-- Posts
CREATE TABLE posts (
    id SERIAL PRIMARY KEY,
    user_id INTEGER NOT NULL REFERENCES users(id),
    title VARCHAR(500) NOT NULL,
    slug VARCHAR(500) UNIQUE NOT NULL,
    content TEXT NOT NULL,
    published BOOLEAN DEFAULT FALSE,
    published_at TIMESTAMP,
    view_count INTEGER DEFAULT 0,
    comment_count INTEGER DEFAULT 0,  -- Denormalized for performance
    created_at TIMESTAMP DEFAULT NOW(),
    updated_at TIMESTAMP DEFAULT NOW()
);

-- Comments
CREATE TABLE comments (
    id SERIAL PRIMARY KEY,
    post_id INTEGER NOT NULL REFERENCES posts(id) ON DELETE CASCADE,
    user_id INTEGER NOT NULL REFERENCES users(id),
    content TEXT NOT NULL,
    created_at TIMESTAMP DEFAULT NOW()
);

-- Tags
CREATE TABLE tags (
    id SERIAL PRIMARY KEY,
    name VARCHAR(50) UNIQUE NOT NULL,
    slug VARCHAR(50) UNIQUE NOT NULL
);

-- Post-Tag junction
CREATE TABLE post_tags (
    post_id INTEGER REFERENCES posts(id) ON DELETE CASCADE,
    tag_id INTEGER REFERENCES tags(id) ON DELETE CASCADE,
    PRIMARY KEY (post_id, tag_id)
);

-- Indexes
CREATE INDEX idx_posts_user_id ON posts(user_id);
CREATE INDEX idx_posts_published_at ON posts(published_at) WHERE published = TRUE;
CREATE INDEX idx_posts_slug ON posts(slug);
CREATE INDEX idx_comments_post_id ON comments(post_id);
CREATE INDEX idx_comments_user_id ON comments(user_id);

    Incident Scenario

    Scenario: Your e-commerce application is slow when loading order history. The schema is:

    CREATE TABLE orders (
    id SERIAL PRIMARY KEY,
    user_id INTEGER REFERENCES users(id),
    created_at TIMESTAMP
);

CREATE TABLE order_items (
    id SERIAL PRIMARY KEY,
    order_id INTEGER REFERENCES orders(id),
    product_id INTEGER REFERENCES products(id),
    quantity INTEGER
);

    The query joins orders → order_items → products for each order. With 1M orders and 5M order_items, it takes 10 seconds.
