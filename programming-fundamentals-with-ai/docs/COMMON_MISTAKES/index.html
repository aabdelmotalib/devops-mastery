    Common Mistakes & How to Avoid Them

    When learning to program, mistakes are inevitable. More importantly, certain mistakes appear again and again across all learners. This guide highlights the most common pitfalls and pragmatic ways to avoid them.

    1. Mistake: Writing Code Before Thinking

    The Problem

    You read a problem, immediately start typing code, and realize halfway through you didn't understand the requirements.

    # ❌ MISTAKE
def process_data(items):
    # Wait... what should this do exactly?
    result = []
    for item in items:
        # I'll figure it out as I go...
        result.append(item * 2)  # Or is it item + 2?
    return result

    Why It Happens

    • Impatience to "get it working"
    • Pressure to produce code quickly
    • Belief that coding is mostly typing

    The Fix

    Always write pseudocode first. Pseudocode is English-like instructions that describe your algorithm.

    # ✅ PSEUDOCODE FIRST
"""
Given a list of items:
1. Create an empty result list
2. For each item in the list:
   a. Multiply the item by 2
   b. Add the result to our result list
3. Return the result list
"""

# NOW write the code
def double_items(items):
    result = []
    for item in items:
        result.append(item * 2)
    return result

    Time saved: 5 minutes of thinking = 20 minutes of debugging.

    2. Mistake: Not Testing as You Go

    The Problem

    You write 50 lines of code, run it, get 5 errors at once. Now you don't know which line caused which error.

    # ❌ MISTAKE - Write everything, then test
def process_user_data(users):
    valid_users = []
    for user in users:
        if user.age >= 18:  # Error 1: user doesn't have .age
            user.status = "adult"  # Error 2: strings aren't comparable
            valid_users.append(user)

    emails = [u.email for u in valid_users]  # Error 3: wrong field name
    send_emails(emails)  # Error 4: function not defined yet
    return valid_users

    Running this gives you 4 errors. Which one do you fix first? You have no idea which lines work and which don't.

    The Fix

    Test after every few lines. Create a small test case for each function.

    # ✅ CORRECT - Test as you build
def process_user_data(users):
    valid_users = []
    for user in users:
        if user['age'] >= 18:  # Test: does user have 'age'?
            user['status'] = "adult"
            valid_users.append(user)

    return valid_users

# Test immediately
users = [
    {'name': 'Alice', 'age': 25, 'email': 'alice@example.com'},
    {'name': 'Bob', 'age': 17, 'email': 'bob@example.com'},
]
result = process_user_data(users)
print(result)  # Does it work? Good. Move on to emails.

# NOW add the next part
emails = [u['email'] for u in result]
# Test it works before going further
print(emails)

    The rule: If you can't test it in under 2 minutes, break it into smaller pieces.

    3. Mistake: Naming Variables x, data, temp, stuff

    The Problem

    # ❌ MISTAKE
d = [1, 2, 3, 4, 5]
x = 0
for i in d:
    x += i * 2
# What does x represent? No idea. Bad variable name.

    Weeks later, you come back and can't understand your own code.

    Why It Matters

    Code is read 10 times more than it's written. If it takes you 30 seconds to remember what x means, that's 5 minutes lost per day across a team.

    The Fix

    Name variables for what they represent, not their type.

    # ✅ CORRECT
user_ages = [1, 2, 3, 4, 5]
sum_of_doubled_ages = 0
for age in user_ages:
    sum_of_doubled_ages += age * 2
# Clear. Anyone reading this knows what's happening.

    Exception: Single-letter variable names are acceptable only: - In math formulas: y = m * x + b - In short loops: for i in range(10): - In obvious contexts: for user in users:

    4. Mistake: Mixing Different Data Types in One Variable

    The Problem

    # ❌ MISTAKE
data = "42"  # It's a string
result = data + 10  # Can't add string + number
# TypeError: can only concatenate str (not "int") to str

    Even worse:

    # ❌ EVEN WORSE
user_id = 123  # It's a number
user_id = "unknown"  # Now it's a string. What?
user_id = None  # Now it's None

    Next person to read this code is confused.

    The Fix

    Keep one variable's meaning consistent. If it starts as a number, keep it a number.

    # ✅ CORRECT
user_id = 123
if some_error_occurred:
    user_id = 0  # Use 0 or -1, not "unknown"

# OR create a new variable for the error case
user_id = None
if valid_user_exists:
    user_id = 123

    Better: Use type hints (Python 3.5+):

    # ✅ BEST
user_id: int = 123  # Explicitly tells others: this is always an int

    5. Mistake: Writing 200-Line Functions

    The Problem

    # ❌ MISTAKE
def process_order(order):
    # Connect to database
    # Validate user
    # Check inventory
    # Calculate shipping
    # Apply tax
    # Process payment
    # Send confirmation email
    # Log activity
    # (200 lines of code in one function)

    This function does too many things. Testing it requires dealing with all of that complexity.

    Why It Matters

    • Hard to test: You have to set up everything to test one piece
    • Hard to reuse: Can't use "just the tax calculation" elsewhere
    • Hard to debug: An error could be in any of 200 lines

    The Fix

    Break it into smaller, single-purpose functions.

    # ✅ CORRECT
def process_order(order):
    user = validate_user(order.user_id)
    item = check_inventory(order.item_id)
    shipping_cost = calculate_shipping(item.weight, user.address)
    tax = calculate_tax(item.price, user.state)
    total = item.price + shipping_cost + tax

    process_payment(user.payment_method, total)
    send_confirmation_email(user.email, order)
    log_order(order)

    return order

# Each function is small, testable, and reusable
def calculate_tax(price, state):
    rates = {'CA': 0.08, 'TX': 0.0625, ...}
    return price * rates.get(state, 0)

    Rule: If your function is longer than a screen, it's probably too long.

    6. Mistake: Not Reading Error Messages

    The Problem

    You get an error:

    Traceback (most recent call last):
  File "app.py", line 45, in <module>
    user.email = user_data['email']
KeyError: 'email'

    Instead of reading the error, you: - Hit "run" again (hoping it fixes itself) - Add a try/catch and ignore the error - Post on Stack Overflow asking "why am I getting an error?"

    Why It Matters

    Error messages are gifts. They tell you exactly what's wrong and where.

    The Fix

    Read the error message bottom-to-top:

    KeyError: 'email'
  ↑ What? The key 'email' doesn't exist in user_data

File "app.py", line 45
    user.email = user_data['email']
  ↑ Where? Line 45. I'm trying to access user_data['email']

Traceback (most recent call last):
  ↑ When? When running this code

    Action: Check if user_data has an 'email' key. If not, handle it:

    # ✅ CORRECT
if 'email' in user_data:
    user.email = user_data['email']
else:
    user.email = None  # or raise an error

    7. Mistake: Copying Code Without Understanding It

    The Problem

    You find a StackOverflow solution, copy it, it works, you move on.

    # ❌ MISTAKE - You don't know what this does
result = list(map(lambda x: x**2 if x % 2 == 0 else x, data))
# You copied it. You don't understand it. Bad.

    6 months later, you need to modify it. You're lost.

    Why It Matters

    • You can't debug it
    • You can't explain it to others
    • You'll copy it wrong next time
    • You're not learning

    The Fix

    If you copy code, understand it line-by-line.

    # ✅ CORRECT - You understand it step-by-step
data = [1, 2, 3, 4, 5, 6]

# The goal: Square even numbers, keep odd numbers as-is
result = []
for num in data:
    if num % 2 == 0:  # Is it even?
        result.append(num ** 2)  # Square it
    else:
        result.append(num)  # Keep original

print(result)  # [1, 4, 3, 16, 5, 36]

    Yes, it's longer. But you understand it. And you can modify it.

    8. Mistake: Not Committing Code to Git

    The Problem

    You're working on a feature. You make changes. Something breaks. You try to undo it manually.

    # ❌ MISTAKE
# You've been coding for 3 hours without Git commits
# Now you have a bug and can't remember what changed
# You can't revert safely

    Why It Matters

    • No safety net: You can't go back
    • No history: What did I change?
    • No collaboration: Others can't work alongside you

    The Fix

    Commit frequently.

    # ✅ CORRECT
git add .
git commit -m "Add user authentication"

git add .
git commit -m "Fix login validation bug"

git add .
git commit -m "Add email verification"

# Now if something breaks, you can revert to any commit
git revert <commit-hash>

    Rule: Commit after every working feature, no matter how small.

    9. Mistake: Writing Comments That Repeat the Code

    The Problem

    # ❌ MISTAKE
# Increment counter
counter += 1

# Check if age is greater than 18
if age > 18:
    # Set status to adult
    status = "adult"

    These comments don't add information. They repeat what the code obviously does.

    The Fix

    Comments should explain WHY, not WHAT.

    # ✅ CORRECT
counter += 1  # No comment needed; it's obvious

# Users under 18 require parental consent per COPPA regulations
if age > 18:
    status = "adult"

    Or document complex logic:

    # ✅ COMPLEX LOGIC - docstring is helpful
def calculate_compound_interest(principal, rate, time):
    """
    Calculate compound interest using: A = P(1 + r/n)^(nt)
    Where:
    - P = principal amount
    - r = annual interest rate
    - n = number of times interest compounds per year
    - t = time in years
    """
    n = 12  # Interest compounds monthly
    return principal * (1 + rate / n) ** (n * time)

    10. Mistake: Premature Optimization

    The Problem

    # ❌ MISTAKE - Optimizing before proving there's a problem
# You write super-complex code to be "efficient"
# Then you realize the bottleneck was somewhere else

    Why It Matters

    • Wastes time: You optimize something that doesn't matter
    • Makes code unreadable: Clever code is hard to maintain
    • Late discovery: You find out after months what the real bottleneck is

    The Fix

    Make it work first, make it right second, make it fast last.

    # ✅ STEP 1: Make it work (ugly is fine)
def find_user(user_id):
    for user in all_users:
        if user.id == user_id:
            return user
    return None

# ✅ STEP 2: Make it right (readable, tested)
def find_user(user_id):
    """Find a user by ID. Returns None if not found."""
    for user in all_users:
        if user.id == user_id:
            return user
    return None

# ✅ STEP 3: Measure. Is it slow? Profile it.
import timeit
# ... measure ...

# ONLY IF SLOW: Optimize
user_map = {u.id: u for u in all_users}  # O(1) lookup instead of O(n)
def find_user(user_id):
    return user_map.get(user_id)

    Rule: Don't optimize what you haven't measured.

    Summary: The Meta-Mistake

    The biggest mistake isn't any single one above—it's not asking for feedback.

    • Show your code to experienced programmers
    • Ask "Is there a better way?"
    • Read other people's code
    • Make mistakes, learn from them, don't repeat them

    You'll make mistakes. That's how you learn. The key is making different mistakes, not the same ones over and over.
